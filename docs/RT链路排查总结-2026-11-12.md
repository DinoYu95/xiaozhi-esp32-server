# 全链路 RT 排查总结（2026-11-12）

本文档汇总 **A/B 拆分**环境下（A：`39.97.x` 智控台 + `zhiban-agent`；B：`172.16.239.226` `xiaozhi-server`）对话 **响应慢（RT）** 的排查结论，基于当次线上/容器 **实测日志**（trace、Server `[RT]`、Agent `[timing]`）。

---

## 1. 架构与观测点

```text
设备 ──WS──► xiaozhi-server (B)
              ├─ VAD / ASR（豆包流式等）
              ├─ 组装 payload → HTTP 流式 POST zhiban-agent (A)
              └─ TTS（火山双流）→ 下行音频

zhiban-agent (A)
  ├─ router (qwen-flash) + load_memory
  ├─ reply_path 分流（parent_tools / xiaozhi_device_tools / llm_reply …）
  ├─ 主 LLM（DashScope chat）
  └─ SSE 流式回 B 机 → 入 TTS 队列
```

| 组件 | 关键日志标记 | 含义 |
|------|----------------|------|
| **xiaozhi-server** | `[RT][round_id]` | 一轮从说话结束到首包下行等 |
| **xiaozhi-server** | `[RT] zhiban-agent 流式首 chunk` | B 机收到 Agent 第一块文本的时刻 |
| **zhiban-agent** | `[timing] api_chat_stream … SUMMARY` | 单请求各 stage 毫秒分解 |
| **zhiban-agent** | `route_decision: reply_path=…` | 走哪条生成链路 |

**注意**：`轮次累计` 在流式 ASR 下可能 **多轮共用同一 `round_id`**（未在每次 `listen_stop` 重开计时），**勿单独当 E2E 总 RT**；以 `E2E 首段下行`、`chat 入口 TTFT`、Agent `SUMMARY` 为准。

## 2. 链路分段与典型耗时（健康 vs 问题）

| 环节 | 位置 | 正常/优化后 | 问题态 | 说明 |
|------|------|-------------|--------|------|
| ASR | B `core.providers.asr` | **~0.01s**（豆包流式） | ~1.5s+（本地 FunASR CPU） | 换豆包后 B 侧已基本不是瓶颈 |
| 意图 / 进 chat | B `connection` | &lt;0.02s | — | `get_functions`、提交线程池 |
| **router** | A `graph_router` | **0.3～0.5s** | 抖动至 1s+ | 每轮固定一枪 qwen-flash，`fast_path=false` |
| load_memory | A | ~15ms | — | SQL 摘要，本轮 skip_vector |
| skill 拉取 | A → manager `web:8002` | ~15ms | — | |
| 拉 MCP/schema | A → B `:8003` internal | **~10～25ms** | DNS 失败时不走 tool | 见下文 P0 xiaozhi URL |
| **主对话 / device_tools** | A | 流式首 token **~0.7～1.2s**（理想） | **invoke 整段 3～3.6s** | 见 §4、§5 |
| Agent → B 首 SSE | A→B | 应贴近 LLM 首 token | **≈ pre_stream（攒全文）** | 假流式 / invoke 完才发 |
| TTS 首包入队 | B 火山 | +**0.3s** 量级 | 火山首句 ~2s（长句） | E2E 之后叠加 |
| **save_memory** | A 异步 | 不挡首包 | **429 + 重试 ~1.4s** | 抢 RPM，见 §7 |

## 3. 案例 A：ASR 已快但总 RT ~3.6s（假流式 + schema 失败）

**Trace**：`9f417b06a304`  
**现象（B 机 xiaozhi-server）**：豆包 ASR ~0.007s，但 `zhiban-agent 流式首 chunk` **~3.61s**。

### 3.1 B 机摘要

```text
ASR 耗时: 0.007s（无声纹）
chat 入口到 LLM 调用前: 0.006s
zhiban-agent 流式响应头/首 chunk: ~3.609s
LLM 首 token: 3.614s | chat 入口 TTFT: 3.620s
（无 E2E 片段在本次粘贴中）
```

### 3.2 A 机 Agent SUMMARY

```text
graph_router=469.6ms
graph_load_memory=14.5ms
graph_context=484.6ms
skill_resolve=15.2ms
llm_xiaozhi_device_tools=19.9ms   # 仅拉 schema 失败
llm_stream_to_first_token=708.2ms # 内部首 token（从开流算起）
llm_first_token=1229.6ms         # 从 ingress 算起
llm_stream_total=3080.0ms        # 主模型整段生成
pre_stream=3601.6ms              # 此时才开始对 B 推 SSE
SUMMARY total_ms=3618.0ms
```

### 3.3 根因（两条叠加）

1. **拉不到 B 机 internal API**（当时 `XIAOZHI_SERVER_URL` / 智控台仍为 `http://xiaozhi-server:8003`，A 机 **DNS 解析失败**）→ `full_reply` 为空 → 回退纯 LLM，但走 **device_tools 分支 `list(_stream_reply_from_llm)` 攒全文** 再 SSE。  
2. **内部首 token ~1.2s，B 机首 chunk ~3.6s** → **用户侧等的是整段 `llm_stream_total`（~3.08s）+ router**，不是首 token。

### 3.4 同时出现的 429（不挡当轮首包）

```text
SUMMARY 结束后 save_memory → POST DashScope → 429 limit_requests
SDK 重试 2 次 → 写入长期记忆失败
[timing] save_memory_async elapsed_ms=1412.2
```

请求上下文：`persist_memory=True`，`speaker_type=unknown`（guest）。

## 4. 案例 B：闲聊也走 device_tools，invoke 讲故事 ~3.9s

**Trace**：`2b7f9d4f443f`  
**用户话**：`都可以，你随便`（intent=`other`，非控设备）  
**现象**：B 机首 chunk **3.907s**，与 `流式结束 3.922s` 几乎相同。

### 4.1 为何走 `xiaozhi_device_tools`（与 intent 无关）

`reply_path` 优先级（简化）：

```text
exit → parent_tools（仅家长）→ xiaozhi_device_tools（设备 MCP 就绪）→ child_shadow → llm_reply
```

`xiaozhi_device_tools_env_ok` 条件：**`device_mcp.ready` 或 `plugin_functions` 非空** 即进入，**不判断本轮是否在聊故事**。

设计目的：设备在线时 **随时可能**「开激光 / 拍照 / 天气插件」，故默认 **bind_tools + tool loop**。

### 4.2 A 机关键日志

```text
route_decision: reply_path=xiaozhi_device_tools intent=other skill=skill_general_chat
GET http://172.16.239.226:8003/.../device/mcp/tools 200  (~11ms)   # P0 内网已修好后
GET .../plugins/schemas 200 (~15ms)
device_tools: 进入 tool loop ... utterance='都可以，你随便。'
device_tools: 第 1 轮无 tool_call，直接文本回复 preview='那我就给你讲一个...小狐狸...'
回复来源=text_llm_tool_loop rounds=1
llm_xiaozhi_device_tools elapsed_ms=3568.9   # llm.invoke 非流式，整段生成
pre_stream=3892.0ms
SUMMARY total_ms=3908.9ms
```

**无** `device_tools 无 tool 回退纯 LLM，真流式` 日志 → 不是「schema 失败回退」，而是 **tool loop 内 `invoke` 一次出长文**。

### 4.3 为何 `llm_xiaozhi_device_tools` 慢

| 因素 | 说明 |
|------|------|
| **`llm.invoke` 非流式** | 必须 **整篇故事生成完** 才返回，才 `pre_stream`、才 SSE |
| **bind_tools** | system 挂 **TOOL_POLICY** + 全套 MCP/插件 schema，prompt 重 |
| **主模型 chat** | 比 router 的 flash 更慢 |
| **输出长** | 用户「随便」→ 模型写长童话 → 输出 token 多，~3.5s 合理 |

### 4.4 同 trace 的 429（save_memory）

```text
17:57:33,411 save_memory 开始
17:57:33,439 429 Too Many Requests
17:57:33,943 429（重试）
17:57:34,813 429（重试）
写入长期记忆失败: limit_requests
save_memory_async elapsed_ms=1404.x
```

发生在 **SSE 已可下发之后**，**不解释 3.9s 首 chunk**，但加剧账号 **RPM 压力**。

## 6. xiaozhi-server 侧结论

1. **`[RT]` 埋点**（`core.utils.round_timing`）：  
   - 看 **ASR 耗时**、**chat 入口 TTFT**、**E2E 首段下行**、**TTS 首包入队**。  
2. **`zhiban_agent_client`**：  
   - `流式首 chunk` 时间应 **对齐 Agent `pre_stream` 或首块 SSE**；若远大于 Agent 内部 `llm_first_token`，多为 **攒全文 / invoke 完才发**。  
3. **TTS（火山双流）**：  
   - 已对 **多分句 sentence_start**、**token 缓冲送火山** 做过优化；E2E 之后仍有 **数百 ms～2s** 级合成（视句长）。  
   - 提交 `80aa7d21`：**subtitle** 供 test_page，重复 sentence_start 时发 subtitle 不清设备缓冲。  
4. **ASR 换豆包流式**：识别 ~**0.01s**，**不能**单独解决 Agent 2.7～3.9s。

## 7. zhiban-agent 侧结论

### 7.1 固定成本

- **router（qwen-flash）**：每轮约 **0.29～0.47s**（案例 B/A）。  
- **graph_context**：与 router + memory 同级，~**0.3～0.5s**。

### 7.2 可变成本（最大头）

| reply_path | 行为 | 首包体感 |
|------------|------|----------|
| **`llm_reply`** | `_stream_reply_then_save` 真流式 | 贴近首 token |
| **`xiaozhi_device_tools`（有 full_reply）** | `run_chat_with_xiaozhi_device_tools` → **`invoke` 全文** → `stream_parent_reply_in_chunks(32)` | **等 invoke 结束**（3s+） |
| **`xiaozhi_device_tools`（full_reply 空，旧）** | `list(stream)` 攒全文 | 同上 |
| **`xiaozhi_device_tools`（full_reply 空，新）** | `_stream_reply_then_save` + `sse_coalesce` | 见提交 `065f905` |

### 7.3 `XIAOZHI_SERVER_URL` 与智控台覆盖

- 容器 env：`XIAOZHI_SERVER_URL`  
- **智控台** `integration.xiaozhiServerUrl` **非空时覆盖 env**（默认 `http://xiaozhi-server:8003`）。  
- A/B 拆分应使用 **`http://<B内网IP>:8003`**，并在 **env + 智控台** 两处一致。  
- 修复后案例 B 已见：`GET http://172.16.239.226:8003/... 200 OK`。

## 8. 429 `limit_requests` 专节

### 8.1 现象

- HTTP **429 Too Many Requests**  
- 错误体：`code: limit_requests`，`You have exceeded your current request limit`  
- **OpenAI SDK 自动重试**（日志可见 `Retrying request in 0.x seconds`）

### 8.2 出现位置（当次日志）

| Trace | 时机 | 模型用途 | 是否挡用户首包 |
|-------|------|----------|----------------|
| `9f417b06a304` | 流式 SUMMARY / pre_stream **之后** | save_memory 抽取 | **否**（异步） |
| `2b7f9d4f443f` | 同上 | save_memory | **否** |

### 8.3 为何容易 429

单轮大致 **DashScope 请求**：

1. router（qwen-flash）  
2. 主对话 / device_tools **invoke**  
3. 流结束后 **save_memory**（guest 仍 `persist_memory=True`）  

多设备 / 多轮并发 → **账号级 RPM** 合并计费，非按设备隔离。

### 8.4 治理方向（产品/运维，未全量落地）

- guest / unknown：**默认 `persist_memory=false`**  
- save **遇 429 不重试**（或最多 1 次）  
- 提 **RPM/PTU**（百炼商务）  
- save **异步队列**，失败丢弃，不雪崩重试

## 10. 待优化项（按优先级）

| 优先级 | 项 | 预期效果 |
|--------|-----|----------|
| P0 | 闲聊 / 非设备意图 **勿默认走 `xiaozhi_device_tools`**，改走 `llm_reply` 流式 | 日常对话首包从 3s+ 降到 ~1s 级 + router |
| P0 | device_tools 内「无 tool_call 纯文本」改 **`stream`** 或边生成边 SSE | 同路径讲长故事也能提前出声 |
| P0 | 智控台 + env **B 内网 IP**（已完成连通时保持） | tool 真可用，减少异常回退 |
| P1 | guest **关 persist_memory**；save 429 不重试 | 减 RPM、减后台抖动 |
| P1 | 技能/提示 **限制闲聊篇幅** | 直接缩短 invoke 时间 |
| P2 | Server：**listen_stop 重开 RT round** | 日志 `轮次累计` 可读 |
| P2 | 百炼 **提额 / PTU** | 高峰多设备 |

## 11. 一句话结论

- **B 机 ASR（豆包）已 ~0.01s，不是当前主瓶颈。**  
- **体感 RT 2.7～3.9s 几乎全部在 A 机 zhiban-agent**：固定 **router ~0.3～0.5s** + **`xiaozhi_device_tools` 的 `llm.invoke` 非流式整段生成（尤其长故事）**；攒完才 SSE，故 B 机「首 chunk ≈ 流式结束」。  
- **429** 主要来自 **流后 save_memory**，不挡首包，但会继续恶化限流。  
- **已发布补丁**仅优化「**无 schema 回退纯 LLM**」；**设备在线的常规闲聊仍走 invoke 慢路径**，需 **路由或 tool loop 流式化** 才能根治。
