Memory 模块：现状 vs 改造目标

基于仓库实现梳理：zhiban-agent（LongTermMemory + load_memory_node / save_memory_node）与 xiaozhi-server（可选 MemoryProviderBase 多实现）。图表可用浏览器直接打开本文件查看。

说明：「接近 ChatGPT 体感」在工程上通常依赖 主体连续检索 + 滚动摘要 + 可选结构化事实，而非单靠向量维度堆砌。 下文「改造后」为目标架构示意，便于对齐迭代范围。

一、现状（As-Is）：智伴 zhiban-agent 长期记忆

1.1 存储与元数据

  • 引擎：LangChain PGVector，PostgreSQL + 向量扩展；集合名 zhiban_long_term_memory（连接串 POSTGRES_MEMORY_URL）。
  • 写入粒度：每条文档是一段抽取后的「事实」短文本（不是整轮对话 raw chunk）。
  • 核心 metadata：user_id、scope（global 或当前 intent 衍生出的 agent 名）、speaker_type（如 owner_child / parent）、uuid。
  • Embedding：由环境配置的模型（如 OpenAI 兼容或 DashScope）生成。

1.2 读取路径（每轮对话前）

  • 入口：load_memory_node（LangGraph 状态）。
  • Query：取最近一条用户消息作为检索 query；若无则用占位「最近对话」。
  • 两次向量检索后拼接：
    • scope = global，top_k = 5，speaker_types 按角色规则（例：主孩子查 global 时包含 owner_child + parent）。
    • scope = current_agent（intent 映射），top_k = 3，speaker 规则另一套。
  • 输出注入：long_term_context → 与 system / messages 一并交给 LLM。

1.3 写入路径（回复生成之后）

  • 入口：main.py 在流式/非流式结束后线程调用 _save_memory_after_reply → save_memory_node。
  • 抽取：专用 LLM prompt 从最近若干轮对话抽出 JSON 事实数组；含过滤（影子任务、系统结束语噪声等）。
  • 分桶：启发式关键词决定事实写入 global 还是当前 agent scope；家长代述孩子信息可映射到 speaker_type = owner_child 存储。
  • 冲突消解：对每条事实 search_similar → 决策 LLM（ADD / UPDATE / DELETE / NOOP）→ add_one / delete_by_ids。

1.5 xiaozhi-server 侧（并行存在）

xiaozhi-server/core/providers/memory/ 提供 MemoryProviderBase 抽象，可实现本地短记忆、mem0 云客户端等；与智伴自建 PGVector 链路可能并行部署，依具体接入配置而定。本页主线以 zhiban-agent 自建长期记忆为准。

1.6 PGVector 里到底是什么：「一条记录」一直在原地更新吗？

不是。当前实现里，PGVector（LangChain）侧存的是多篇向量文档，每一篇对应：

  • 一段抽取后的短文本（一条「事实」）；
  • 自己的 embedding；
  • metadata：user_id、scope、speaker_type、uuid（文档 id）等。

每次对话结束（且开启持久化）：save_memory_node 可能抽出多条事实，对每一条分别走一遍「相似检索 → 决策」，而不是把整个库揉成一行。

决策（示意）对库里数据意味着什么
ADD 新增一篇文档（新的 uuid、新向量），库里的条数 +1。
UPDATE 代码路径是先 delete_by_ids 删掉被选中的旧文档，再 add_one 写入修正后的新文本——本质是删旧 + 插新（新向量），不是「表里永远只有一行、只改这一行的文本」那种心智。
DELETE 按 id 删除对应文档。
NOOP 本条候选事实不写库。
小结：库里通常是越来越多条「事实文档」（减去被删掉、被替换的旧条）。读取时 load_memory_node 用相似度 Top-K 在多文档里捞若干条拼成 long_term_context，并不是每次只读「固定那一行」。

过渡：原架构的主要问题 & 为什么要做后续改造

A. 现有方案已经做对的部分（不必全盘否定）

  • 用向量库做跨轮、跨会话召回，方向正确；
  • 抽取事实 + 冲突消解有利于控制上下文长度、去掉废话；
  • speaker_type、scope 分流减轻角色串味。

B. 体验上容易「不如 ChatGPT 顺滑」的根因（为何要演进）

  • 检索 query 过窄：仅用最近一条 user 当 query，用户承接上文、换说法、指代省略时，向量召回容易偏题或空召回。
  • 只有「事实碎片」，缺「叙事层」：仅存抽取句，对话脉络、场景、前后因果大量丢失；模型只能靠几条 bullet 自己脑补，整合感不稳定。
  • global / agent 双桶 + 关键词分桶：启发式难免分错桶或重复写，跨 skill/intent 时可能出现「该记的记在某一 scope，另一路检索搜不到」之类断层。
  • 主体维度若与孩子/设备未对齐：仅用 user_id（会话维度）在多孩、多设备场景下可能串味或检索不准（视你们线上绑定策略而定）。
  • 没有滚动摘要层：远期内容无法压缩成可持续注入的「脉络段落」，长期对话越多，越依赖稀疏事实命中，体感会像「偶尔记起一句」而非「连贯上下文」。
  • 写入链路强依赖抽取：抽漏则永远不入库；抽噪声则污染向量；冲突消解再调用 LLM，有成本与延迟。

C. 改造目标要解决什么（对应关系）

痛点目标架构里的抓手

二、改造目标（To-Be）：接近 ChatGPT 式「跨会话整合」

2.1 设计原则

  • 主体优先：检索过滤以 child_id / 家长账号等稳定主体为主键；session_id 用于衰减或加权，不作为唯一围墙。
  • 三层记忆：情景块（Episodic）+ 滚动摘要（Consolidated）+ 结构化事实（Profile/Facts）。
  • Skill：统一向量索引 + metadata 中的 skill 做 boost，避免物理分库导致跨 skill「失忆」。
  • 读路径：并行召回 → 可选 Rerank → 固定顺序打包上下文（Facts → Summary → Episodic → 近期原文）。

2.3 与现状的差异（对照表）

维度 现状（As-Is） 目标（To-Be）
存入内容 主要为 LLM 抽取的短事实向量文档 增加原始情景切块检索；摘要层；可选结构化事实表
检索 Query 最近一条 user 文本 当前问题 +（可选）轻量意图；摘要通道可恒注入最新摘要片段
scope / skill global vs intent→agent 两次检索 倾向统一索引；skill 为 metadata 加权
跨会话 依赖同一 user_id 下事实是否被正确写入 显式 child_id 等与时间衰减；摘要承接远期语境
整合感 依赖模型从若干事实串中自行整合 通过分层材料（事实/摘要/片段）提高可控性与命中率

2.4 分阶段落地（便于排期）

  • P0：写入与检索统一主体维度（child/parent）；metadata 补齐 session、时间戳；评估 scope/skill 合并策略。
  • P1：上线滚动摘要生成与注入；摘要可向量化参与召回。
  • P2：结构化 facts 表 + 少量 bullet 注入（类 ChatGPT「记忆」）。
  • P3：Rerank、观测指标（空召回率、重复记忆率）、删除/合规策略。
